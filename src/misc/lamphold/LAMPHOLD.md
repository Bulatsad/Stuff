# LAMPHOLD — «борец за ламповость» (RTS в духе Stronghold Crusader)

> Слой: `game` (`src/misc/lamphold`). **Roadmap и план реализации** — модуль ещё не начат; этот док фиксирует согласованный план и по мере реализации станет шпаргалкой по устройству игры.
> Не дублирует правила проекта (`AGENTS.md`) и roadmap движка (`ARCHITECTURE.md`) — только ссылается.
> **Обновлять при любом изменении кода lamphold** (см. AGENTS.md, «Документация модулей»).
> Сверено: 2026-10-01

---

## Назначение и границы

- **Lamphold — 2D-изометрическая RTS в духе Stronghold Crusader** (луп «построй → добыча → защита»). Название — «lamp» (лампа) + «hold» (крепость): «борец за ламповость в эру бездушных игр». Точный клон невозможен и не планируется (копирайт Firefly Studios: ассеты, дизайн, имена) — вдохновение механиками и духом.
- Целевая платформа — Windows/MSVC, как у всего проекта; паттерн «lib + тонкий exe»; игра — плагин к единому эдитору (см. ARCHITECTURE.md «Эдитор — плагин-модель»).
- **Границы MVP (согласовано с автором):**
  - тайл-карта (изометрические ромбы) + ортографическая камера;
  - стройка: склад, хижина лесоруба, каменная стена;
  - крестьянин: A* до дерева → рубка → доставка дерева на склад;
  - лучник со снарядом-стрелой;
  - простой враг: атакует здания/юнитов;
  - условие победы/поражения;
  - одиночная игра = локальный сервер (паттерн gravelands, см. GRAVELANDS.md).
- Всё остальное (AI-лорд, цепочки ресурсов, армии, осады, кампания, мультиплеер) — после MVP, см. «За скобками MVP».
- Слои: `lamphold-*` зависят от beng/blib; `lamphold-common` — только от blib-int/beng-core. Нижние слои о lamphold не знают.
- Что НЕ в этом доке: правила кодирования (AGENTS.md), roadmap движка (ARCHITECTURE.md), детали ECS (BENG.md), рендер (GRAPHICS.md), сеть/репликация (SERVER.md, CLIENT.md), образец паттерна игры (GRAVELANDS.md).

## Инварианты и поток данных (целевые, по мере реализации)

### Слои и владение

- **Сервер — авторитет на всё игровое**: тайл-мапа, экономика, юниты, бой живут на сервере; клиент шлёт только команды (никогда позиции/состояния). Репликация состояния — движковая (см. SERVER.md).
- **Тайл-мапа — данные грида**, а не ECS-сущности: terrain + occupancy (кто занимает тайл) на сервере; клиент получает статику при старте (синхронизация мира — как в gravelands, начальный вариант — процедурная/фиксированная карта на обеих сторонах, Welcome-синхронизация — позже).
- **Рендер тайлов** — через единый ECS-рендер сцены (сущности + `MeshRenderComponent`, слой `Ground`), как в gravelands; никаких прямых `renderTarget.draw(...)` в хостах.
- **Здания/юниты/снаряды** — ECS-сущности с игровыми компонентами (сериализуемыми, `ISaveLoadable`), регистрируются на сцену по стабильным именам (`T::componentTypeName`).
- **Спрайты/текстуры-плейсхолдеры** — живут **вне git** (`assets_external/`, в `.gitignore`): копирайтные материалы Stronghold допустимы только как временные плейсхолдеры пет-проекта и будут заменены собственными/свободными ассетами до любого публичного использования. Загрузчик ассетов берёт путь из констант — замена тривиальна.
- **Один сетевой путь** для одиночной игры, пары сервер+клиент и PIE (local-server mode — паттерн gravelands).

### Таймстеп (гибридный, как gravelands)

- Сервер — фикс. тикрейт 60 Гц (аккумулятор, `serverFixedDelta`); клиент — переменный dt кадра. Экономика/бой считаются только на сервере.

### Команды игрока (протокол)

- Кодек — расширение паттерна gravelands (`PlayerCommand`, payload-байты): `Select` (клиентская подсказка/клик), `PlaceBuilding {buildingType, tile}`, `MoveOrder {entityId, tile}`, `AttackOrder {entityId, targetId}` (фаза 4). Сервер валидирует всё (деньги/ресурсы, занятость тайла, принадлежность юнита игроку).

## Roadmap

Оценка: **~2-3 месяца** неспешной работы. Чекпоинт каждой фазы — собираемый билд (`cmake --build ../build --config Debug`) + обновлённые доки затронутых модулей.

### Фаза 0. Движковые пробелы (blib/beng) — ~1.5 недели

|---|--------|------|
| 0.1 | **Ортографическая проекция**: `IsometricCamera` сейчас только перспективная; добавить орто-режим (напр. `setOrthographic(...)` или класс-режим). Дефолт остаётся перспективным — gravelands/model_viewer не ломаются | `blib/graphics/isometricCamera.h/.cpp`, затронет `rendercontext` — GRAPHICS.md |

Критерий: орто-камера рендерит, A* проходит тест, RNG детерминирован от seed, все существующие таргеты собираются.

## Подводные камни и ожидаемые грабли

- **Ортопроекция (0.1):** затронет `RenderContext`/шейдеры/пост-пасс (near/far, матрицы); дефолт должен остаться перспективным — регрессии gravelands/model_viewer недопустимы.
- **Тайл-пикинг:** математика world↔tile для ромбов + края карты; проверять обе оси.
- **A*:** диагональная стоимость, динамическая occupancy (построенная стена инвалидирует пути), недостижимость цели (юнит стоит на месте, не дёргается).
- **Сеть:** все проверки правил — только на сервере; клиент рендерит состояние, а не домысливает (предикшн — только движковый, как в gravelands).
- **PIE/local-server:** guard'ы регистрации типов/систем обязательны (перезапуск Play→Stop→Play), иначе фейлы как в раннем gravelands.
- **Копирайт:** текстуры Stronghold — только плейсхолдеры вне git; перед любым публичным показом — замена (см. «Инварианты»).
- **Изометрия + ECS-рендер:** порядок слоёв (Ground→Shadow→AlphaTested→Opaque) важен, юниты за зданиями — сортировка по Y-таилу (примитивы MVP сглаживают проблему, для спрайтов — отдельная задача).
